# Git 提交规范

决策日期：2026-10-21。
该文件是对提交、Conventional Commits、独立分点、实现细节与功能说明的明确要求。
本文件约束后续新增或整理的提交消息，不要求改写既有提交历史。

格式依据 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)。中文叙述、技术名称保留原名、编号正文及 emoji 位置是本项目在其基础上的约定。

## 消息格式

```text
type(scope): emoji 摘要（中文叙述，技术名称保留原名）

1. 一项独立改动，说明问题或功能、关键实现及效果。
2. 另一项独立改动，单独阅读也能理解。
```

`type` 使用小写英文；`scope` 表示改动模块或能力，可以省略，也可以直接使用实际技术名称。保留主分支常用的 emoji 风格，使用时放在冒号和空格之后，类型前缀始终位于行首。标题与正文之间空一行。

## 具体规则

| 编号 | 规则 |
| --- | --- |
| CC-001 | 标题和正文的解释性文字以中文为主。文件名、配置文件、API、SDK、类名、协议字段、框架名和版本号使用实际名称，例如 `manifest.json`、TypeScript、Cordis、SlotCore、UUID；不为中文化而改成含糊的替代词。 |
| CC-002 | 标题采用 `type(scope): description` 结构；模块说明主要改动区域，例如 `导入`、`前端`、`Git`，不堆叠文件名。 |
| CC-003 | 标题直接概括修复的问题或新增的能力。“优化代码”“完善功能”“更新内容”等不能单独作为摘要。 |
| CC-004 | 正文使用编号列表，按独立改动分点，通常 2–4 条仅供参考。简单改动允许只写 1 条，不为凑数量拆点或为少列几条而合并不同功能。每点单独阅读也能理解，必要时可以使用多句话。 |
| CC-005 | 修复类说明“什么问题、通过什么关键改动修复、修复后的效果”。保留理解修复所需的做法，例如统一识别文件路径、检查响应是否属于当前请求、数据库事务回滚与文件恢复。 |
| CC-006 | 新增类说明“增加什么功能、采用什么关键实现、能做什么”。技术名称须与其作用相连，例如 Cordis 管理插件生命周期，SlotCore 管理界面插槽。 |
| CC-007 | 准确和易读优先于字数及信息密度。保留改动对象、关键实现、适用条件和结果，不把多个动作压成需要猜测的术语。文件名或关键接口有助于定位问题时直接写出；删减重复和无关细节，不机械省略技术标识。 |
| CC-008 | 消息只描述本提交实际包含的改动。未实施的建议、尚未修复的问题和其它批次的工作，不得写成已经完成；计划与待办留在对应审查文档。 |
| CC-009 | 按同一问题或能力拆分提交，必要测试随功能或修复同批提交。共享文件按相关代码块拆分，消息不得用最终工作区的全部改动代替本批差异。 |
| CC-010 | 写入验证结果时，只记录针对该提交快照实际执行的检查及结果。旧快照通过不代表当前通过，配置 CI 不代表远程作业通过；未验证的范围明确说明。 |
| CC-011 | 仅在真实破坏兼容性时使用 `!` 或 `BREAKING CHANGE:`，并说明影响及迁移方式。内部重构、增加新接口但保留旧接口，不自动构成破坏性变更。 |

## 类型选择

| 类型 | 使用场景 |
| --- | --- |
| `feat` | 新增用户或插件可使用的功能、接口与能力 |
| `fix` | 修复已有功能的错误行为 |
| `build` | 依赖、构建配置、打包与安装器改动 |
| `ci` | 持续集成工作流、检查顺序与诊断产物 |
| `docs` | 规格、使用说明、接口文档和验收记录 |
| `refactor` | 保持外部行为不变的结构调整 |
| `perf` | 有依据的性能改进 |
| `test` | 独立的测试调整；不用于拆走功能或修复所必需的测试 |
| `style` | 不改变语义的代码格式调整；界面新功能和交互变化按实际改动选择 `feat` 或 `fix` |
| `chore` | 不属于上述类型的维护工作，仍须写明具体内容 |
| `revert` | 撤回既有提交，说明撤回对象及原因 |

模块是否省略、使用哪个 emoji，不影响类型按实际改动选择。不要使用 `update`、`misc` 代替具体类型来汇总无关工作。

## 技术名称与表达完整性

中文是解释问题和功能的叙述语言，不要求把技术名称全部翻译成中文。读者需要知道修改了哪个文件、接口或框架时，直接使用其实际名称。例如写“扩展 manifest.json”，不要只写“扩展清单”，让读者猜测具体对象。

简洁是删除重复信息，不是省略理解改动所需的上下文。不要为了标题更短、每点只占一行或固定分点数量，省掉修改对象、关键条件及因果关系。一个分点可以用两句话，先说明改动，再解释实现和效果。

需要解释技术概念时，保留原名并补充作用。例如“Cordis 管理插件启停，SlotCore 管理界面插槽”；既不只罗列依赖，也不以生造的中文词组代替技术名称。

## 写法示例

以下示例用于说明消息写法，不表示当前工作区已生成对应提交或完成验收。

### 修复问题

```text
fix(导入): 🐞 修复重复导入标识变化与失败恢复问题

1. 修复重复导入同一库文件时元件编号变化的问题，统一识别文件路径，找到已有记录并保留原 UUID。
2. 增加导入失败恢复，写入前保存文件备份和恢复记录，数据库事务失败时回滚并还原库文件。
```

### 新增功能

```text
feat(前端): ✨ 新增类型化插件 SDK 与共享运行时

1. 新增前端插件加载与扩展能力，采用 DSH 的 Cordis + SlotCore 管理插件启停和界面插槽。
2. 新增 TypeScript 插件 SDK，为侧栏注册、视图扩展和宿主接口调用提供类型检查。
3. 支持插件共享运行时，构建时将 React 留给宿主提供，避免插件重复打包和加载多份实例。
```

### 表述对照

| 不充分的表述 | 建议写法 |
| --- | --- |
| 支持清单第二版与可取消任务 | 扩展 manifest.json 并支持任务取消。 |
| 支持新版插件配置 | 扩展 manifest.json，分别声明 Python 功能入口和前端界面资源。加载前检查宿主与 SDK 的版本兼容性。 |
| 请求代次失效保护 | 为每次请求分配递增编号。只有最新编号的响应可以更新状态，避免旧响应覆盖当前结果。 |
| 修复重复导入问题 | 修复重复导入同一库文件时元件编号变化的问题，统一识别文件路径，找到已有记录并保留原 UUID。 |
| 采用 Cordis + SlotCore | 新增前端插件加载与扩展能力，采用 DSH 的 Cordis + SlotCore 管理插件启停和界面插槽。 |
| 优化元件计数 | 修复忙态响应会清空“全部元件”计数的问题，保留最后有效统计，收到完整心跳响应后再更新。 |

## 审查要点

- 标题能否看出修复了什么问题，或增加了什么能力。
- 每个分点是否独立，是否写出必要的实现方式及效果。
- 文件名、技术名称和关键条件是否准确保留，是否因翻译或压缩而变得难懂。
- 内容是否与本批差异一致，是否将未完成事项或未执行的验证写成完成。
- 功能或修复所需的测试是否随同提交，验证结果是否对应当前提交快照。
